# Notes about the development process for ´Keyrus Dataset Analyzer´

1. Understand the problem and break it down to its basic parts.
2. Create a GitHub repository for the project.
3. Create a project-description.md file with a comprehensive explanation of the problem, requirements and expected outcome.
4. Connect Vibe CLI and Claude to the repository via MCP.
5. Create a skill for Mistral vibe using Claude to generate a Development process based on the project-description.md, and using OMIMO's NUPP and p1.express project management methodology.
`Why Mistral? Tokenomics... because Claude's tokens are much more expensive, so I rely on smaller and cheaper models for easier tasks, and Claude for code intesive ones.´
6. Create a skill for Claude to follow the Development process generated by Mistral, using the project-description file as context.
7. Start the development using Claude in VS Code.

## Issues encountered

- **File-size limit contradiction.** `development-process.md` stated a 50MB upload limit in three places (Milestone 2.1's done-when, the File Parser Checklist, and the Deferred/backend rationale), while the Open Questions section resolved it at 15MB. The orchestration skill's reconciliation step caught this and flagged it rather than silently picking one — required a decision from me on which number was authoritative (15MB, since it was the resolved answer) before fixes were applied.
- **API-key delivery contradiction, self-inflicted.** I edited the Open Questions "API key setup" answer mid-session (UI-entered keys → `.env`-only, since the no-backend policy rules out a UI path for secrets), but Milestone 4.1's task text still said "via environment variable **or UI input**." The skill's reconciliation caught the mismatch on the next read and it was fixed to `.env`-only, plus a `.env.example` task was added since keys can no longer be entered through the app.
- **Dual-LLM-provider routing left ambiguous.** The Open Questions resolve on two providers (originally DeepSeek for data-analysis calls, Google AI Studio for report-text generation) but never say which specific feature (data dictionary / business insights / client questions) uses which. The roadmap carried a best-guess routing (DeepSeek for 4.2/4.3, Google AI Studio for 4.4), explicitly marked as an assumption. **Resolved:** confirmed as correct when Phase 4 was dispatched (see the DeepSeek→Groq swap below for the provider that actually ended up on 4.2/4.3).
- **No headless-browser tooling on this Windows dev machine.** Neither `chromium-cli` nor Playwright was available to screenshot/click-through the app after Phase 1, so verification fell back to lint/type-check/build passing plus a manual code trace of each done-when condition. I ran `npm run dev` myself and confirmed the upload flow worked end to end.
- **DeepSeek account had no funds.** Real API verification during Milestone 4.1 (LLM infrastructure) authenticated successfully against DeepSeek but every call returned HTTP 402 "Insufficient Balance" — the key was valid, the account just wasn't funded. I flagged this and asked whether to proceed anyway (building against an unusable provider) or reroute. **Your decision:** switch the data-analysis provider from DeepSeek to Groq (Llama 3.3 70B Versatile), and make both providers' model IDs configurable via `.env` (`VITE_GROQ_MODEL_ID`, `VITE_GOOGLE_MODEL_ID`, `VITE_GOOGLE_FALLBACK_MODEL_ID`) instead of hardcoded, so a future provider swap doesn't require touching code again. Milestone 4.1's clients, and Milestones 4.2/4.3's `**Provider:**` lines, were updated to match; DeepSeek's client code was left in place but unused.
- **LLM output needed a shape the UI could stay ignorant of.** The original roadmap's Milestone 4.2-4.4 tasks each described their own ad-hoc output shape (e.g. "KPIs show as metrics cards") with no shared contract — exactly the setup that caused Phase 2's three parsers to come back with mismatched shapes needing after-the-fact reconciliation. Before Phase 4 dispatch, you specified that since the app targets different business cases, LLM responses needed a single JSON schema per content type — with its own description/tags/quantity range — so the UI could render and filter generically instead of hardcoding layout or fixed counts. **Solution:** designed a shared `InsightItem`/`InsightGroup` contract (zod-validated) as part of Milestone 4.1, with per-type quantity bounds (KPIs 2-5, insights 3-5, recommendations 3+, questions 2+, one dictionary entry per column) declared as configurable data — built once, consumed by all three parallel content-generation milestones instead of each inventing its own shape.
- **Malformed JSON from LLM responses.** Raw `JSON.parse` on an LLM's response is fragile — models occasionally wrap output in prose, leave a trailing comma, or get cut off mid-response. You asked for `jsonrepair` plus regex-based verification on every LLM-generated response to significantly cut down on broken-structure failures. **Solution:** layered parsing in `src/lib/llm/client.ts` — markdown-fence stripping → bracket-depth-aware extraction of the outermost JSON substring (so leading/trailing prose or an enclosing array doesn't get mis-captured) → strict `JSON.parse` → `jsonrepair` fallback for near-misses (trailing commas, unquoted keys, single quotes, unbalanced/truncated brackets) → parse again. Verified against 9 real-world malformed-response patterns; anything still not matching the expected shape is caught by the existing zod schema validation rather than crashing.
- **LLM trigger behavior needed a real decision, not an assumption.** Phase 5 is where the data dictionary, business insights, and client questions panels would finally be mounted for real — before wiring them in, I asked whether all three should auto-generate on upload or wait for the consultant to ask, since each of the three costs a real, paid API call. **Your decision:** only the data dictionary (which explains the dataset's own structure) auto-generates; business insights and client questions stay manual, per-tab "Generate" buttons, so a casual upload doesn't silently burn three API calls.
- **Report format needed a decision too.** Milestone 5.3's download-report task left the format open ("PDF or Markdown"). **Your decision:** Markdown now (no new dependency, fits the project's small-and-finished philosophy), with a fully-formatted PDF explicitly documented as the intended finished-product goal for later — see the comment at the top of `src/lib/report/markdownReport.ts`.
- **Business Insights panel was silently violating the manual-trigger decision.** A code review pass at the end of Phase 5 (before closing out the branch) caught that `BusinessInsightsPanel` had carried an auto-triggering `useEffect` since it was first built in Milestone 4.3 — it went unnoticed because nothing rendered the panel yet at that point. Once Milestone 5.2 wired it into the always-mounted results view, that dormant bug would have fired a real, paid LLM call on every upload, directly contradicting the manual-trigger decision above. **Solution:** removed the auto-run effect, added an explicit "Generate business insights" button matching the other two panels' pattern, and re-verified live in a browser that it no longer auto-fires.
- **Redundant re-parsing left over from Phase 1.** The same review pass found that `FileUploadPanel` still rendered Phase 1's original preview component, which independently re-parsed the just-uploaded file with its own naive parser — duplicate work and a duplicate, overlapping summary once Phase 5's real pipeline (and its Overview tab) existed. **Solution:** removed the Phase 1 preview subsystem entirely (6 files: the component, its table/summary-bar children, its hook, its naive parser, and its types) now that the Overview tab shows the same information from the real, already-computed `AnalysisResult` — no second parse, no duplicate UI.
- **A subtler correctness bug in how generated content reached the download report.** The same review also caught that all three LLM panels notified the parent of new content via `.then((result) => onDataChange(result))` chained directly on the request promise — which resolves to `null` for a request that's since been superseded or aborted, not just for a genuine failure. A fast double-click or a new upload landing mid-request could have overwritten good report data with `null`. **Solution:** moved the notification into an effect keyed on the loading hook's own `status`/`data`, which is already guarded against exactly this (a stale request's result never sets `status` to `'success'`) — fixed identically across all three panels rather than patching one and leaving the same bug in the other two.
- **Groq hit real rate limits during live testing.** After Phase 5 shipped, you ran the app for real and hit Groq HTTP 429s generating the data dictionary and business insights — a provider-capacity problem, not a bug in the retry/error handling (which already surfaced it as a clear, user-facing "please wait and try again" message rather than crashing). **Your decision:** switch the data-analysis provider a second time, from Groq to Mistral, and set it up with both a primary and fallback model id (`VITE_MISTRAL_MODEL_ID` / `VITE_MISTRAL_FALLBACK_MODEL_ID`) — matching the pattern already used for Google AI Studio — so a future rate-limit hit degrades to a second model instead of failing outright. Verified with a real call against the live Mistral API before considering it done. `groq.ts` (like `deepseek.ts` before it) is kept in the codebase but no longer wired into any active routing.
- **Data Dictionary silently re-ran its LLM call on every dataset switch.** Found via live testing of the new Phase 7 shell. Root cause: `useDatasetSession` rebuilds a fresh `AnalysisResult` object every time a stored dataset loads (including switching back to one already viewed), and `DataDictionaryPanel`'s auto-generate effect only tracked "have I already generated for *this exact in-memory object*" — it had no memory that spanned a switch, so it burned a real, paid API call and threw away the previous result every single time. **Solution:** wired the `llmOutputs` storage slots Phase 6's `PersistedDataset` shape already reserved for exactly this — a freshly-generated dictionary now persists to the dataset's own IndexedDB record, and `useLlmRequest` gained a `seed()` method so the panel can feed straight from a persisted result instead of re-running the LLM call. Switching back to a previously-documented dataset now shows it instantly. Added a dedicated end-to-end test (`e2e/data-dictionary-persistence.spec.ts`) that generates two datasets' dictionaries for real and proves the first one comes back byte-identical, with no regeneration, on switch-back.
- **Same live testing surfaced a related, not-yet-hit correctness risk.** `BusinessInsightsPanel`/`ClientQuestionsPanel` stayed mounted across a dataset switch the same way the dictionary panel did, but without any persistence backing them — meaning switching datasets could show dataset A's generated insights while the rest of the screen was already displaying dataset B's data. **Solution:** keyed all three LLM panels to the active dataset's id in `MainViewport`, so React gives each dataset a clean slate on switch (the dictionary re-seeds instantly from storage per the fix above; insights/questions require a fresh "Generate" click per dataset until Phase 8 persists them too).
- **A string/id column ("order_id": "ORD-50276"...) was misclassified as a date column.** Also found via your live testing — the Column Detail card showed a nonsense "DATE RANGE" section (earliest "50000-01-01") for a plainly non-date column. Root cause: `dates.ts`'s free-form fallback parser accepted *any* string containing a letter and handed it straight to `Date.parse()`, which happily (and wrongly) interpreted the trailing digits of an ID like "ORD-50276" as a year. **Solution:** the fallback now requires a recognized month name before it will even attempt `Date.parse()`, plus a sanity upper bound on the resulting year as a backstop. Added 4 regression tests (`src/lib/analysis/dates.test.ts`) covering ID-like and SKU-like columns (must NOT detect as dates) alongside real ISO and free-form month-name dates (must still detect correctly).
- **Sidebar layout/contrast feedback from the same testing pass.** The left sidebar scrolled away with long page content (hiding its "Download PDF Report"/"Upload new dataset" buttons off-screen) and that the center viewport read as slightly *darker* than the sidebars rather than lighter. **Solution:** the shell is now pinned to the viewport height with only the center content scrolling internally (top bar/sidebar/footer stay fixed in place), and the color tokens were swapped so the chrome (top bar, sidebar, footer) carries the muted tone and the viewport is the lighter surface, in both themes.
